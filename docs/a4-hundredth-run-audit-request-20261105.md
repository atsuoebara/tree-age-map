# A-4 第3弾「100回目のラン」独立監査依頼（2026-11-05）

状態：**開発ブランチの試作、未マージ・未公開**。既存A-4初30kmは正式完了済み。今回の100回目だけ独立監査対象。

## 保存済みデータの実コード確認
- `index.html` 内の `fetchCloudRuns()` は、ログイン本人の `runs` を `deleted_at=is.null` で、50件ずつ最終ページまで取得し、取得完了後に配列を返す。
- クラウド保存済みラン一覧 `renderCloudRowsList` は `cloudRows` を年/月で絞るが、DB上の全保存済み行をカウントするわけではない（選択期間により画面上の件数が変わる）。マイルストーンは**期間絞り込み前の同じ `fetchCloudRuns()` 全件**を用いる。
- 現行 `runs` スキーマにはラン種目の信頼できる正規化列がなく、未知の取り込み元を「ラン」と断言できない。**第3弾の対象集合は第2弾と同じ、`source=fit` または `source=strava` かつ正しい `strava_id` のランのみ**。GPX/TCX/Garmin/Intervals/その他は数えない。これは「全保存済みランの生涯100回目」ではない。
- FIT経路はスポーツ確認を経たこと、Stravaの稼働中 `strava-sync v46` が Run/TrailRun/VirtualRunのみを保存することはPR #28で監査済み。将来同期が変われば検証見直し。Strava紐付けでは保存距離・ルートは元レコードの可能性あり。
- 既存スキーマの `id` はrunsの主キー。同じIDが取得配列に2度現れる場合はデータの欠損・ページング重なりの可能性があるため、**件数を認定せずエラー表示**する（勝手な重複削除もカウントもしない）。

## 判定ルール
1. 対象源（FIT/Strava認証済み）、`deleted_at == null`、主キーIDが正の安全な整数、`started_at` が正しく解釈可能な実走開始日時のランだけ数える。
2. 30km走との相違：100本目は距離下限もGPSルートの有無も不要。**GPSなしのFITランも対象**。
3. 取得順・登録順ではなく、`started_at` 昇順。同時刻はruns主キーIDの数値昇順。0～99件は未達、100件以上はソート後の100番目（0始まり配列[99]）を表示。
4. 削除・過去ランの追加で変動。本人専用・毎回全件再計算、DB変更なし。
5. `fetchCloudRuns()` の取得が完了したときのみ初30km・100本目双方を計算。途中失敗は両方エラー表示。
6. 100本目の **GPS地図ジャンプはこの弾では設けない**（GPSなしの対象を含むため）。既存初30kmの地図ジャンプ機能は維持する。
7. UIは「100回目のラン（対象記録内）」と限定。100本未満なら「対象記録 N本 / 100本」。達成なら日付・保存距離・対象記録の合計本数。日英でGPSなし・他ソース除外・過去記録追加での変動・地図導線の対象を説明。
8. 例：クラウド全件が1817でも対象集合が小さければ回数は1817とは一致しない。一般のラン履歴件数と混同させない表現を求める。

- `a4-milestones-preview.js`: 既存初30kmパネルの下に100本目カードを追加。既存の `fetchCloudRuns()` 戻り配列を共用。所有者・世代ガード、ログアウト時の消去、日英更新を維持。
- `index.html`: 2本のスクリプトのキャッシュ版数更新だけ。
- `scripts/test-a4-milestones.cjs`: 既存テストに99/100/101・逆順・過去追加・同時刻・削除・不明ソース・GPSなし・欠損時刻・重複IDなどを追加。
- **合成テスト52アサーション合格**、core/preview構文チェック合格。DB・同期API・追加API・費用は変更なし。

## むせへの監査重点
1. 対象集合が「100回目のラン」と表示して誤解を招かないか。種目保証の範囲と、対象外のソースの扱いを含めて批判的に評価。
2. 同一ID重複時の処理、別IDでの同一活動重複、ページングの順序安定性。**保存済み行のIDがユニークでも、二重取り込み行がある場合に100本目を誤認し得る**。これを許容できるか。過去の重複統合方針との整合性。
3. 99/100境界、日時の欠損/不正、同時刻ID、GPSなし、deleted_at削除、FIT/Stravaのみの判定。
4. 「対象記録」件数がクラウド総数と異なることの表示説明の十分性。
5. 初30kmの地図移動、表示、英語対応やログアウト保護を壊さないか。
6. 本番へのマージ可否、および追加すべき試験や停止条件。

**独立監査と運営者の承認が揃うまでmainにマージしない。**
