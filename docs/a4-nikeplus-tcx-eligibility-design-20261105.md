# A-4 第5弾 設計案 v0.1：Nike+時代のTCX記録を安全に年輪へ反映する

- 日付: 2026-11-05
- 状態: **設計・独立監査依頼のみ。未実装、未マージ、未公開、DB更新なし**
- 開発原則: 既存機能を壊さない／スマホ最優先／追加費用0円／本人の記録は本人の同意なく公開しない

## 背景（本人確認＋現行仕様）
利用者本人は古いTCX記録を「Nike+ のやつ」と説明している。この発言は当該データの来歴を確認する重要な手がかりである。ただし、**保存済みのすべてのTCXがNike+に由来するという機械的証明ではない**。

読み取り専用集計で、保存済み1,817行中、A-4現行対象1,434行、対象外383行を確認。対象外内訳は TCX 328、source NULL 46、Garmin 6、Intervals 2、Stravaだがstrava_id欠損1。数値は当時のスナップショットで増減しうる。

現行 `index.html` の `buildActivityFromTCXText` はTCX `Activity` の `Sport` 属性を小文字化し、値が存在して `running` 以外なら拒否するが、**Sport値なしは受け入れる**。`source='tcx'` のみがクラウド `runs` に保存され、元のSport属性・原本識別情報・取込時のスポーツ検証結果を永続化していない。`runs` に `sport_type` 等の列は存在しない。

従って、TCX328行へ一律 `source=fit` を付けたり、既存 `verifiedImportedRun` に `source='tcx'` を無条件追加したり、本人の発言だけを根拠にすべてを認定することは**禁止**する。GPS軌跡・距離・日付だけでは種目確証にならない。

## 提案フェーズ

### P0 — 読み取り専用の差分可視化
既存A-4の対象数は変えず、本人ログイン時だけ、元の保存レコードを最小限のフィールド（`id,source,activity_date,started_at,distance_km,name` 等）で分類する検討用導線を**設計**する。対象外にはTCX・不明・Garmin・Intervals・Strava-IDなしを別区分で出す。原則として名前や活動日等の個別情報はブラウザ内だけに表示し、パブリックページ・ログ・分析・GitHubに保存しない。新しいUIは監査完了まで本番に置かない。

### P1 — Nike+起源の証拠評価
1. 元のNike+エクスポートTCXが残っている場合、ヘッダー、`<Activity Sport="Running">`、ファイル名・ID等の**出所と種目の両方**を本人が確認できる方法を検討する。データは公開しない。
2. 取り込み前のSportに `Running` が明示されたと確認できる場合は自動認定の候補。Sport欠損・出所未確認のものは「不明」として残す。
3. 原本とDBの対応付けは、日時・距離だけで同一活動を断定しない。マッチングの一意性と誤認・重複IDを検証する。自動認定でない場合は**保存済みレコードIDにひもづく本人の明示確認**に限定する。
4. 利用者本人の「Nike+のやつ」という発言だけで、旧データすべての種目を機械的に保証できるかは別途監査判断。

### P2 — 最小権限の本人確認フロー（実装前の設計審査）
種目証拠が足りない場合は、本人が各候補を「ランと確認済み／不明／除外」と明示できる案を検討。確認前OFF、全件一括承認や推定による初期ONは禁止。本人確認の日時・対象run ID・確認根拠・撤回方法を記録する方式を比較する。**既存 `runs.source` を書き換えない**。新しいDBテーブルが必要なら別PRと独立RLS監査を必須とし、無承認でDDLや書き込みはしない。

### P3 — 認定前後の差分プレビュー
現行のA-4節目数、初30km、100/500/1000、次の節目と、仮に本人確認済みの記録だけを追加した場合の結果を**読み取り専用で比較**できる仕様を目指す。
- 2013年までのデータを足すと初30kmや100本目の日付が大きく動く場合がある。日付変化・本数変化は本人承認前に知らせる。
- 保存レコードの同一IDは重複認定せずフェイルクローズ。別IDで同じ活動が重複していれば、既存ルールどおり別本として数える旨を開示。
- A-4現在の計算器と既存確定結果は維持し、候補プレビューと厳密に分離する。認定反映はさらに監査と本人明示承認を経た後。

## 独立監査の問い
1. Nike+起源という本人情報の扱い、TCX `Sport` 必須性と、Sport欠損の保留判断は妥当か。
2. 既存TCX328行の種目が **DBからは再証明できない** 制約を正しく認識しているか。
3. 当該本人・当該保存レコードIDに限定する認定・撤回・監査証跡の設計は十分か。他ユーザーのTCXを自動認定する事故を防げるか。
4. 原本との同定、タイムゾーン、日付/距離許容差、複数ファイルと同一活動、重複行などでの誤認防止。
5. 現行初30km・100/500/1000・次の節目の **既存認定を勝手に変更しない**、計算・表示の完全分離。
6. 秘密情報、個人行動履歴の保護、RLS、追加コスト0円、iPhone最優先。
7. 実装開始を許可できる最小スコープはP0か、P1か。追加条件を列挙すること。

## 停止条件
この設計PRの段階では**コード変更、DB操作、認定フラグ追加、全件の自動ラン認定、公開データ変更を行わない**。むせによる独立設計監査とユーザーの判断が揃うまでは既存の1,434件基準を維持する。
