# A-4「年輪の節」仕様案 v0.2（むせ設計監査反映）

作成: 2026-11-05
状態: **設計案・実装前**。アプリ本体・本番DB・公開設定は未変更。むせのv0.1設計監査で挙げられた定義を明文化。実装後の試験・独立監査・運営者最終承認が別途必要。

## 目的と段階
本人の保存済みランから、走り続けた節目を静かに振り返れる表示を作る。競争・ランキング化はしない。
- **第1弾：初めての30km走のみ**。もっとも判定が安定し、過去の取り込み順や回数に依存しにくい。
- **第2弾候補：100回目のラン**。母集団と既存一覧・重複処理が実コード上で一致することを検証してから。
- **第2弾以降：市町村ごとの初到達**。Territoryの既存判定を使い、一覧の表示方式を決定してから。
- 段階によらず、共有画像・公開URL・通知・自動投稿・SNS連携は対象外。

## 全候補に共通するデータ条件
- 対象は**ログイン本人の、削除済みでない保存済みラン**。runs.deleted_at がnullであることを必須とし、対象種目は **Run / Trail Run / Virtual Run**（実際の正規化後の種目値は実装前に確認）とする。
- 走行日時が無い記録は節目判定にも対象件数にも含めない。日時は保存済みランの**実走開始日時**を使い、取り込み日時や日付文字列順は使わない。時差・同時刻処理を既存データ仕様と照合する。
- 順位が必要なときは、開始日時の昇順、同時刻の場合は**runs主キー（数値なら数値順）**を使い、ソース固有IDをタイブレークに使わない。
- 保存済みラン一覧で採用している既存の重複処理後の集合を唯一の母集団とする。独自の推定重複検出・削除はしない。実際の一覧のデータ取得経路と同一にできない場合は回数の節目を公開しない（差分注記だけで安易に代替しない）。
- 保存済みランの追加・修正・削除や後からの過去分取り込みに応じて**表示時に再計算**する。恒久的に確定した「生涯初」の事実としては扱わない。
- 他人の記録・公開ランキング・B-1匿名集計は参照せず、DBへの新規書き込みも行わない。

## 第1弾：初めての30km走
- 対象はRun / Trail Run / Virtual Runの保存済みランのうち、**GPSルートが有効な単独の1ラン**。GPSの無いVirtual Run／インドア走は今回の30km判定に含めない（100回目とは条件が異なる）。
- 距離は**保存済みラン一覧で表示に使う元の保存距離そのもの**を比較する。保存単位がメートルなら **30,000m以上**を達成とし、kmで保存されているなら同じ実値を **30.000km以上**で判定。丸めて表示した値から再計算しない。29.999km、29.995kmは未達。
- 対象のうち距離閾値を満たす最初のランを実走開始日時順（同時刻ならruns主キー順）で選ぶ。複数のランの合計距離で達成としない。
- 該当記録がなければ「まだ記録されていません」。日時・距離の欠損や有効GPS判定が曖昧な記録は不確実な達成として推定表示しない。
- **判定表示の注記**：「Runner's Ringsに取り込まれた記録の範囲で判定しています。過去のデータ追加・削除により表示が変わる場合があります。」
  EN: “Based on activities imported into Runner's Rings. Results may change when older activities are added or records are deleted.”

## 第2弾候補：100回目のラン
- 対象は削除済みでなく、実走開始日時を持つRun / Trail Run / Virtual Runの**保存済みラン一覧に表示される既存の重複処理後の全件**。GPSなし・ルートなし・トレッドミル（インドア）も回数に含む。
- 100件目を開始日時昇順、同時刻はruns主キー順で決定。99件以下は未達。後日の過去分追加で100件目の対象が変わる可能性がある。
- 記録への導線はGPSルートがある場合は地図・対象ランへ、ルートなしの場合は**「🏃 ランニング記録（件数）」の保存済みラン一覧**へ案内する。
- 実装前に「保存済み件数」と「地図で描画される活動件数」が異なる既知ケースを再検証し、100回目がどちらを数えているかUIで誤認させない。既存一覧との一致が実証できなければ第2弾を延期する。
- 日英のデータ範囲・再計算注記は第1弾と同様に付記する。

## 第2弾以降：市町村ごとの初到達
- **Territory（A-2）の既存アクティビティ単位の市町村帰属判定をそのまま利用**し、独自の境界判定や新しい地理データは導入しない。
- 各市町村について「**既存の市町村判定で、その市町村が記録された最初のラン**」を実走開始日時順で求める。同時刻はruns主キー順。
- 判定は走行GPSポイントを基礎とする。GPS点とGPS点を直線で結んで通過しただけの市町村が必ず記録されるとは限らない。
- 初期UIは**最近の初到達を最大10件**表示し、全件の履歴表示は別途設計・監査する。ページングや画面負荷を増やさない。
- 結果は本人だけに表示し、地域別の公開集計や走行開始終了地点の公開は行わない。Territoryの既存判定結果と相違がある場合は実装を延期する。

## UI方針
- まず第1弾だけ本人向け「年輪の節」プレビューとして出す（達成名称、日付、距離、対象ランへの導線、注意書き）。
- スマホ優先、日英両対応。未達表示も日英実装。ルート・距離・日付・画面状態に無理な推測値を使わない。
- 登録済みランの表示に必要な既存の閲覧権限を利用。新規DBテーブル、外部API、有料サービスは追加しない。

## 実装前の読み取り専用確認
1. runsの主キー、deleted_at、種目値の正規化、開始日時・時区間・距離の実保存単位、GPS有効判定を現行コード／スキーマで照合する。
2. 保存済みラン一覧の取得・重複処理と地図の活動集合の相違を検証する。第1弾は数の節目ではないため回数機能は未実装。
3. 既存Territoryの「市町村×アクティビティ」帰属元とGPSポイント基準を読み取り専用で確認する。第1弾では地域節目を未実装とする。
4. 合成サンプルで境界値29.999/30.000km、日時欠損、同時刻、削除、過去ラン追加、GPSなし、種目除外、複数ソース重複を試験する。回数機能を実装する段階で99/100/101件も試験。
5. 機能・言語切替・スマホ表示の回帰試験、むせ独立監査、運営者最終承認。成功したデプロイと本番ファイル一致を公開完了条件とする。
