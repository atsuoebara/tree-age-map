# PR #128：公開コード更新・旧タブ・停止通知の合成シミュレーション（2026-11-14）

## 前提と目的
PR #126のiPhone実機では、架空の5区間を表示した後にSafariの「戻る→進む」でbfcache (persisted=true) が表示され、結果が消去されたと本人が確認。PR #127では旧タブの撤去問題が**未解決**であると整理した。

本PRでは、**既に開いたJavaScriptが、公開版の差し替え／撤回を知らない場合**を、外部通信・ファイル・本番UIを使わずに模擬する。ネットワークで実際に新しい版を取得するテストではない。

## 隔離シミュレーター
`src/rings-now-open-tab-rollout-simulation.mjs` はメモリだけで動く仮想の公開版と複数タブを持つ。各タブは読み込み時の版 `loadedBuild` と、そのタブが最後に受け取った版 `knownBuild` を分ける。

- `publish('v2')`：公開側がv1→v2に変わったと想定。**開いたタブには自動通知されない**。
- `withdraw()`：公開側の撤回を宣言。**タブが必ず通知を受けるわけではない**。
- `miss(tab)`：通信不能、オフライン、通知なし、チェック未実行などで、古いタブが更新を知らない経路を表す。
- `observe(tab)`：仮想的に「新しい停止／版シグナルを受け取った」経路を注入する。これは本当のブラウザ通信ではなく、暗号検証や安全な取得方法の証明でもない。
- `hide`、`pagehide`、`pageshow(persisted=true)`、`invalidate`：旧タブがローカルの失効イベントを受けた場合を模擬。再表示しても失効状態を解除しない。

全状態の `verifiedSafe`・`realFitAllowed`・`productionAllowed`・`oldTabGuaranteedStopped` は常に **false**。仮想的にバージョンが一致しても、結果は `requires_manual_review` が上限。元のPR #127監査モデルを呼ぶだけで新しい公開入口には接続しない。

## 重要な観察：停止通知を受けない旧タブ
シミュレーションで公開版をv2へ更新しても、古いタブに停止シグナルが届かなければ、古い版v1のまま「自分は最新だ」と判断し続ける場合がある。これは**古いタブが安全に停止したという意味ではない**。モデルが返す `requires_manual_review` も処理許可ではない。

旧タブへの通知不能は、同一タブ内のpagehide等の失効処理だけでは解決できない。また、**公開ファイルの削除・差し替えだけで既存タブの実行停止を保証できない**。HTTPキャッシュ、CDN、bfcache、Service Workerは別々に検証する必要がある。

## 将来の安全設計に向けた選択肢（未決定）
1. 実FITデータを扱う前に毎回、有効な版と撤回状態を外部で確認する方式：通信が発生する。通信禁止という従来方針と矛盾しないか、要求先がFITやIDなどを収集しないか、オフライン時の遮断動作を別監査する必要がある。
2. 通信を使わずページの有効期限を短くする方式：期限の間は撤回を知らせられず、古い既存タブの強制停止保証はできない。端末の時計、スリープ、bfcache復帰時も検証が必要。
3. 公開版の切替・撤回は安全停止の補助に留め、実FITを処理する公開ページそのものを出さない方式：現時点でのデフォルト。実FITの本人端末上の入力、公開HTML、機能本番ONの許可は別々。

これらは設計案であって採用済みではない。実FIT配信方式Aの14項目はすべて証拠審査待ち。追加費用0円、iPhone優先、既存機能破壊禁止。

## 変更範囲と独立監査
新規4ファイル（隔離シミュレーター、テスト、文書、CI）のみ。index、SW、公開HTML、DB、カレンダー、実FITパーサー、既存機能、Rings Now本番OFFを変更しない。公開ページは増えない。

むせ確認：更新前の既存タブに通知が届くとは限らないこと、停止シグナル受信時と未受信時の結果、2タブ独立性、bfcache・ローカル失効の不可逆性、処理許可が常時falseであること、動的実通信をしていない限界、最新CI／回帰、差分4ファイル、監査のみ・マージ禁止。
