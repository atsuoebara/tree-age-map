# 「今を知ろう」C4受信・真正サンプル結線案（設計のみ / 2026-11-12）

状態：**設計ドラフト。PR #67 の隔離枝に記録。未監査・未マージ・本番接続なし。**
基準：Issue #96、直近のむせ C1〜C4隔離ゲートの合格。本人限定・大会/TT/記録測定の1回だけ、走行開始から**8日（691200秒）**。過去の一括取り込みなし、年輪は現状保持。分析結果は本人が画像で保存・任意共有することを優先し、無期限の結果履歴は初期版で不要。

## main の現状（読み取り専用ソース照合）
- `supabase/functions/garmin-activity-push/index.ts` の `sanitized()` は activityDetails 受信時に `samples` から緯度・経度しか残さない。時刻・累積距離・心拍はここで落ちる。後で `parsed()` が GPS route と run メタデータを作るが、精密な1km経過ラップ復元には不足する。
- `supabase/garmin-activity-reliability.sql` の `garmin_receive_details` は、connection_version と owner 付きで `garmin_activity_inbox.payload` を作り、既存 `garmin_commit_activity` は現在の接続と権限をロック照合して `runs` へ保存/duplicate判定する。
- `garmin_commit_activity` はその**同じDBトランザクション**で inbox の `payload='{}'` と `state=saved/duplicate/ignored` を設定する。元詳細サンプルの後日取得経路はない。権限失効/接続削除で未処理 inbox が消去される。
- `runs` には Garmin の `source_external_id='garmin-api:'+activityId` が入り、ユーザー単位の一意索引がある。既存カレンダーは `runs.activity_date` を使っており、`started_at` とは区別する。
- **現在の本番DBに`ingested_at`列が存在するとは未確認**。隔離C4の `OwnedRun.ingested_at` は実装予定契約の型であり、mainの実スキーマを証明しない。既存 run の `created_at` が採用可能かはスキーマ検査後に決める。実データは未読。

## 提案：元の年輪を壊さない最小構成（未承認）
1. Garmin `activityDetails` の**新規受信時だけ**、時刻・累積距離・任意心拍を含む最小限のサンプルを検証・サニタイズする。受信ID、summaryId、ユーザーID、接続世代、activity開始時刻を確定する。未検証フィールド名に勝手に依存せず、実際のGarmin仕様と受信フィクスチャの照合を先行する。位置座標は分析用データへコピーしない（既存年輪のGPS routeは従来どおり）。
2. **受信→保留→保存**の既存経路で、`garmin_commit_activity` が本人のrun新規insertに**成功した場合のみ**、run IDを返して新しい本人限定・非公開の最小サンプル保管先へ同じトランザクションで紐づける。`duplicate`/過去ラン/ignored/取り消し/失効は保存しない。前からあるrunを事後更新しない。受信レコードとrunのuser_id、Garmin活動ID、summaryId、connection_version、started_at、receipt時刻を一組で整合させる。
3. **保管先候補は新規の小さな非公開テーブル**（例：`garmin_private.race_samples`）。主キーまたは一意制約はowner・run・外部活動IDの組、run削除／接続世代変更・権限失効・ユーザー削除に伴う削除、サービス専用権限を設計する。対象をGarmin新規取り込みに限り、既存runsのGPS/Journal/年輪を変更しない。
4. **単独の分析要求時**はサーバでログインを検証し、選択した未削除runを本人スコープで読み、同じトランザクションまたは整合スナップショットで有効な接続世代と当該活動のサンプルを取り出す。クライアントはrun ID、本人が入力したintent/confirmedだけを送り、`samples`・user ID・活動開始日時・受信日時・`requestedAt`・8日ポリシーを送れない設計にする。途中削除/失効競合の確定点を定義する。
5. サーバ時計と実際の走行開始時刻で8日（192時間）以内かを判定し、隔離C1/C2/C3/C4品質ゲートへ渡す。JOGは本人選択段階で拒否。短い5kmのラップは表示しても、6本以上の完全1km条件を満たさない場合は練習提案を出さない。
6. 8日を過ぎたサンプルは、失効/ユーザー削除などの即時削除に加え、**保管期限の上限**を正式に決定して定期消去する。期限切れランを後日取得して延命させない。保存・受信に失敗した場合、元の年輪のラン保存は従来どおりに行えるよう、障害境界を設計する（ただし「サンプルだけ孤児化」や二重ACKは不可）。
7. 診断結果はその場で表示し、本人操作で端末へ画像保存/OS共有。初期版で長期結果テーブル、自動公開、リンク公開はしない。結果画像にユーザーID/GPS軌跡/住所/トークンなどを含めない。

## なぜDB変更なしでは難しいか
- 現行runには詳細サンプルが残らず、inboxはcommit完了時に空にされる。
- サンプルの**真正性・同じ活動との結合・再接続時失効・削除時消去**を保証するには、別のサーバ保管先（DBないし同等の安全なストレージ）とトランザクション設計が不可避。
- ブラウザ上のローカルキャッシュや本人提供JSONでは、Garmin由来の真正性を証明できない。
- 既存PR #68 は「結果保存テーブル等」向けの広いStage A設計であり、そのまま採用せず、**原データの短期保持と結果画像**に必要な最小変更を比較する。既存RPCの置き換え/引数増加は旧クライアントやリトライの互換性に配慮する。
