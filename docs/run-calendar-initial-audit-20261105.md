# 「マイランニング記録」カレンダー表示 初期実装・独立監査依頼（2026-11-05）

## 状態
**PR：ドラフト、未マージ・本番未公開。** 既存のクラウド一覧・地図・記録データに書き込みなし。先行PR #46のiPhone表示最終承認はまだ別途必要。

## 目的
保存済みランが1,800本を超えると、目的の記録を一覧から探しにくい。現行一覧を残したまま、年/月を選び、日付セルの距離から記録を探せるようにする。iPhone・0円・既存機能保全を優先する。

## 新しい導線・表示
- ラン記録ボタンの隣に「📅 カレンダーで探す」を設置。ログイン本人だけで利用する従来の `cloudRunsPanel` を開き、カレンダータブに切り替える。
- 従来の記録一覧と新しい月間カレンダーを二択のタブで切替。現行 `cloudRunsList` / 新しい順・古い順 / 名前編集 / `focusCloudRun` を保持する。
- 年・月のセレクトと前月・翌月の矢印。古いNike+時代まで年選択で移動可能。
- 各日に**その日保存されたレコードの距離合計**を表示。同日複数本なら本数も併記。日付タップで元の行ごとに名称と距離を表示し、その行タップで既存の走行ルートへ。
- 月合計も「この月の**保存済みラン**」と明記して本数・距離を表示。距離欠損は不明と開示。
- 日本語・英語表示、幅の狭いiPhone向けの7列グリッド。各セルは最低52px以上でクリック可能、既存のメイン機能タイルは変更しない。

## 日付境界・月間年輪との集計定義
1. **日付キーはDBに保存済みの `runs.activity_date` （`YYYY-MM-DD`）を唯一の正とする。** `started_at` は表示カレンダーの日付算出には使わない。UTC時刻に `.toISOString().slice(0,10)` を適用して日本時間の夜ランを前日へずらす事故を防ぐ。
2. `activity_date` が不正・欠損なら該当月に入れず、日時を勝手に推定しない。うるう年等の日付を検証。
3. 日付セルおよび月合計は、ログイン本人の**保存済みクラウド `runs` 全件（deleted_at除外）**を使う。A-4の「種目確認済み1,434本」とは別。TCXなどをカレンダーから排除しない。
4. 既存A-1「今月の年輪」は `RunnerMonthlyRings` の `activities` 配列とローカルDateで集計している。カレンダーは `runs.activity_date` による保存済みデータだけを集計するため、月間年輪と必ずしも一致しない。**総量の名称・母集団を分け、同じ数字だと誤認させない注記を画面に配置**した。統一は別途設計・監査が必要。
5. もともとの `activity_date` 自体が取り込み時に誤っていればこのカレンダーでは修正できない。元データを変更せず別問題として扱う。

## プライバシーと失敗時の安全性
- 従来の `fetchCloudRuns()` と `cloudRows` だけを利用。追加のDB/API呼び出し、localStorage、共有・公開、計算結果の外部送信なし。
- 取得開始時の `currentUser.id` を保持し、取得完了時・キャッシュ後に現在ユーザーと異なる場合は結果を破棄。カレンダー表示の許可も `rrCalOwner===currentUser.id` を条件にする。
- ログアウト・ユーザー切替時に日付選択・表示された個別記録を消し、従来の一覧モードへ戻す。過去の他人の記録が新しいユーザーに表示されないことを重点検査。
- サーバ側の所有者RLSは変更しない。追加の永続化はしない。
- 行の日時・名前は `textContent` で描画し、HTMLインジェクション経路を作らない。
- Cloud取得失敗時は、現行の一覧機能の既存エラー処理を維持し、カレンダーで誤った所有者のデータを表示しない。

## 既存機能保護
