# Rings Now — 実スナップショット接続の事前ゲート v0.1（設計のみ）

**状態：HOLD / 接続未承認。** 本文は設計・検証要件の整理であり、Supabase・Auth・DB・カレンダー・FIT・本番設定に変更を加えない。

## 確認済みの前提
- #137〜#148 は隔離した関数・架空のページ取得でのテスト。**実Auth JWT、RLS、鮮度、完全な一貫性は未証明**。
- #141/#147 の offset+ID昇順検査では、並行削除による **昇順のままの欠落** を見抜けない。
- #148 の二重走査は一部の変化を検出するが、変更→復元（ABA）、2回とも同じ欠落、終了直後の変更は検知できない。取得の時間・負荷も倍増。
- 既存カレンダーの `cloudRows` / IndexedDB キャッシュは、freshな認証済みのRings Nowデータとして転用不可。

## 推奨する検証候補：認証付きの一貫したDB側スナップショット取得
将来別承認の下で、Supabase Auth JWTに紐付いたサーバー側の**一つの一貫性境界**（DBトランザクション/RPC等）から、user_idで制限した必要6列のみを取得する案を優先検証する。これは**仕様候補**であり、現行スキーマ・利用可能権限・プラン制限での実装可否は未確認。

- 実行主体は認証済み利用者。サービスロール等のRLS迂回をクライアントへ配らない。
- owner UUIDはクライアントの申告だけでは信用しない。DB側で `auth.uid()` と実行文脈を厳密照合する。RPCが `SECURITY DEFINER` の場合は権限・search_path・実効RLS・漏えい経路を追加監査。 `SECURITY INVOKER` 等も実スキーマで評価する。
- 対象は所有者本人の未削除ランのみ。列は `id,user_id,activity_date,distance_km,started_at,deleted_at`。経路・GPS・心拍・FIT内容は取得しない。
- 確定時点の単一の一貫した集合で読み取れることを検証。**単なるキーセットページングや2回読みはトランザクションの代わりにならない**。
- 1,000件上限は**fail-closed**（上限超過時は一部1000件を見せない）。実ユーザーへの妥当性と取得性能を別途確認し、恣意的な上限引き上げ禁止。
- ログアウト／ユーザー切替／A→logout→A／重なった読み込み／画面離脱で結果・ガチラン確認を直ちに失効させる。ページ取得中の最新性判定には世代ガードを使う。
- 8日＝691200秒の起点はrunの `started_at`。終了時間・取り込み時間ではない。開始時刻 null では既存の公開入口を有効にできない。停止を勝手に除外せず、自動ポーズ時の不正確性を表示する。
