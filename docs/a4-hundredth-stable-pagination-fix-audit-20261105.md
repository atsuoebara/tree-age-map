# A-4 第3弾 PC実機エラー修正・独立監査依頼（2026-11-05）

## 発端と判明した実装上の問題
ユーザーのPCスクリーンショットで、初30kmと100回目の両方が「確認できませんでした」となる現象を確認。iPhoneでは以前、初30kmの達成日と距離を確認済み。

- PR #33 は `fetchCloudRuns()` のあと、`first30km()` と `hundredthRun()` を**同じtry/catch**で呼び出し、後者に例外が出ても両方をエラーへ変えていた。初30kmが成功しても表示されない明白な回帰経路。
- `fetchCloudRuns()` の既存ページングは `order=activity_date.asc` のみで、同日複数ランが50件ページ境界にかかる場合、順序不定により一部のIDが重複取得される可能性がある。`hundredthRun()` は重複IDを安全側に例外として拒否するため、100回目の結果を止める可能性がある。
- **注**：実際のユーザーデータに重複IDが存在した証拠やHTTP失敗のログはまだない。原因の最終断定はしない。取得自体がHTTPエラー等で失敗する場合には両方エラーとなる設計を維持する。

## 修正内容（A-4に限定）
1. `index.html` の `fetchCloudRuns(options = {})` に任意の `stableOrder: true` オプションを追加。その場合のみ `order=activity_date.asc,id.asc` にする。通常のラン一覧など既存呼び出し元は旧順序のまま。
2. `a4-milestones-preview.js` は `fetchCloudRuns({stableOrder:true})` を使用して一度だけ全件取得。完了後、**初30kmと100回目の各計算を独立したtry/catch**で実行する。100回目の計算だけ失敗した場合に初30kmの達成表示が維持される。
3. サーバーからの全件取得失敗では従来どおり両方エラーとし、部分取得で節目を認定しない。
4. 既存の `hundredthRun` の重複IDを拒否する安全条件は緩めない。DB・Edge Function・日英文言・ユーザーの記録は変更なし。
5. `index.html` のA-4 preview参照版数を `20261105-stable-fix-01` に更新。
