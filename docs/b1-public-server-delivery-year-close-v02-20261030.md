# B-1 公開配信方式・確定年の締め：設計決定案 v0.2
作成日 2026-10-30 / **監査用の設計文書。実装・公開・正式同意受付は未開始。**

## 前提：むせ監査（19:02〜19:12）の条件付き合格と4条件
1. **配信経路：公開GitHubリポジトリ・静的HTML・JSON・ビルド成果物・Git履歴に集計値を置かない**。
2. 確定年の締めを明示し、後から届いた過去記録を公開値へ黙って反映しない。
3. 最小人数・寄与支配・丸め幅は合成データT1〜T9の結果で決定。
4. 最終同意文面に国×完了年、年単位原則1回、撤回後の停止と限界を記す。

## アーキテクチャ（提案として確定方針にする項目）
**静的フロントエンド + サーバー側の都度認可読み取り**を採用する。集計値を配信するのは認証・プライバシー判定を実施するSupabase Edge Function等の専用サーバー経路のみ。公開GitHubにはUIとAPI呼び出しコードだけを置き、値・キャッシュ・過去スナップショットをコミットしない。

APIは個々の要求のたびに非公開DBの状態を確認：
- 緊急停止/全体公開OFFなら応答データなし
- 対象年の公開許可・同意規約版・集計世代・失効フラグ・匿名性審査結果のいずれかが不一致なら応答データなし
- 公開値を返すときでも国コード・対象暦年・丸めた距離に限定し、同意者数、寄与者上位、正確な距離、集計日時、世代番号や内部抑制理由は返さない
- レスポンスは `Cache-Control: no-store, private` を基本とし、CDNやサービスワーカーが過去の値を無条件で保持しないか実機と配信経路で確認。ブラウザや第三者の保存済み画面を完全回収できるとは表現しない
- 公開権限を持つサーバー側のみが非公開候補・審査結果へアクセス可能。匿名クライアントからのDB/RPC直接参照を拒否
- 同意撤回/記録訂正を受けたら**先に配信停止フラグ/世代を失効**し、その後の再計算・監査を行う。旧値との差分が漏れる可能性があれば当該セルを非表示のままにし、安易に数値を差し替えない
- 運用上は非公開DBに「承認済み年の一回限りスナップショット」「公開世代」「個別セル有効/撤回停止」等が必要。ただし現状のDB構成はまだ未確認で、テーブル・権限定義・Edge Function仕様は**次工程で現状を読取確認したうえで作る**。既存の合格済み非公開基盤を直接変更しない
- 障害でサーバー確認できない場合は公開数値を出さない。失効の競合・同時撤回・配信中断時の原子的整合を隔離環境で検証

## 「確定年」の締め方案：監査用の暫定値
対象は **UTCの1月1日00:00から翌年1月1日00:00直前までの完了した暦年**。年越し日付解釈は実データのラン帰属方式との整合を検証する。
- **候補の締め：翌年4月1日00:00 UTC**（2026年活動なら2027年4月1日）。約3か月間は遅延同期や訂正を非公開の候補へ反映し得る。暦年終了から締めまで、公開数値は出さない。
- 4月1日時点で参加希望＋その規約版の正式同意が有効な、実際にその国で正距離を走ったユーザーのみを判定候補にする。遡及的な活動利用を許す説明・同意が必要。
- 締め後、匿名性/差分攻撃テストに通ったセルのみ、一度だけ公開候補にできる。**締め=自動公開ではなく、別途監査承認が必須**。
- 4月1日以後の過去活動の追加・修正で数字を静かに更新しない。訂正・削除・同意撤回に起因する法的/倫理的必要性があれば配信停止を先行し、旧値比較が危険なら**再表示しない**。
- 毎年の締め時刻・対象日付のタイムゾーン・後追い同期への説明を公開前に実データモデルに合わせて最終決定。これは**提案値であり確定・承認済みではない**。

## 合格条件（実装前に固定）
P1: 静的GitHubページ/公開ビルド/旧コミットに個人由来の集計値が一切入らない
P2: 公開OFF・dirty・世代不一致・同意版不一致・監査未承認時は必ず空応答
P3: キャッシュ有効/無効・複数端末・並列撤回・旧世代要求・ネットワーク失敗で古い数値を再配信しない
P4: 2026年の活動データは2027年4月1日より前に公開できず、締め後の遅延取込でも公開値が変化しない
P5: 人数・支配性・丸め・外部知識・複数年比較で一意または狭い範囲で寄与者を推定できる場合は非表示
P6: Todayや既存の全体統計と母集団を混同せず、他の国×年セルとの連立推定も検査
