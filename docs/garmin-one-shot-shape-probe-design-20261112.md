# Garmin Activity Details ワンショット形状検査 — 実装前設計ゲート v0.1

日付：2026-11-12　状態：**設計のみ／本番導入は未承認**  
ユーザー条件：新しいランをわざわざ走らない、Garmin Developer Portalへのログイン不要、年輪取り込みを壊さない、追加費用0円、個人情報・Secretを露出させない。

## 1. 今回分かった前提
- 現在のGarmin Push受信はSecret設定訂正後、稼働済み（本人確認）。2026-10-22の未着問い合わせは古い。
- 本番 `garmin_activity_inbox` は saved 34、duplicate 5、ignored 1 の計40件が処理済みで、`payload != '{}'` の件数は**全状態0**（2026-11-12読み取り集計）。既存DBからは生サンプルを復元できない。
- `garmin-activity-push/index.ts` は `readBody` → `enqueue` → `sanitized()` → `garmin_receive_details` の経路。`sanitized()` は時刻/累積距離/心拍を捨て、既存GPS座標のみ保存。
- 現行処理は失敗時503でGarmin再送を要求し得る。**診断の例外・遅延でこの応答を変更してはいけない。**
- Githubの合成フィクスチャ内 `heartRate` はGarmin現行正式スキーマの証拠ではない。`heartrate` の綴りも二次資料由来で未確認。

## 2. 推奨する最小構成（まだ実装しない）
ユーザーが承認した後、1回限りの**内部用集計プローブ**を短期間だけ有効にし、次に自然に届くActivity Detailsから**項目の存在と型の集計だけ**を得る。

候補：
1. PushリクエストがSecret照合・サイズガード・JSON解析に成功した後、`enqueue(body)` を既存どおり実行する。集計コードは**本番ACK/キュー/解析/年輪インポートと非依存**で動き、失敗は完全に握り潰す。
2. **診断結果には活動ID・ユーザーID・GarminID・時刻値・距離値・心拍値・GPS座標・token・URL・外部IDを含めない**。フィールド名は固定許可リストのみ。
3. プローブ有効化の設定は**公開Web UIやクライアントから操作不可**。サーバー内部の明示的に期限付きフラグのみ（自動停止と手動停止、最大1回の成功検査）。期限の管理が実装できないなら本番プローブを実施しない。
4. **結果をどこへ残すかは設計レビュー後に確定**。候補A：本番サーバーログへ許可された集計値1行だけ（ログ保持期間・アクセス権・自動無効化が要検証）。候補B：非公開の合計件数だけを最小テーブルに保持（新規DBと費用・バックアップ・削除を伴うため、当面は推奨しない）。
5. サンプルを匿名加工したつもりでrawペイロードをファイル・DB・ログ・Issue・PRへ載せることは**絶対にしない**。
6. 新しく走る必要はない。自然に届くランで判定可能な設計。データが届かなければ「未確認」と記録し、ユーザーに実走を強制しない。

**重要な限界**：「項目名の存在」は計測データを保存できることの証明ではない。次の段階でGarmin固有の単位、起点、時間単調性、サンプルギャップ、長距離サンプル数を別検証する。GPSだけで正確な1kmラップは復元しない。

## 3. 処理の分離とフェイルオープン（年輪優先）
- 新規プローブが壊れても既存`enqueue`の結果・HTTPステータス・重複判定・worker再試行は同じ。診断処理は決してawaitしない外部ネットワーク要求を追加しない。
- 各サンプルを逐次走査して許可キーの存在/数値型だけ数える。配列オブジェクトをclone/serializeしない。上限は本番の既存8MB HTTPガードに加え診断側で個別20,000サンプル、100活動を上限とし、超過時は診断スキップ。
- Deno CPU予算や悪意あるネストでACKに影響が出るリスクが残るため、本番組み込み前に最大入力・障害注入・並列負荷試験が必要。**「try/catchだから安全」とだけで合格しない**。
- プローブはrun選択や診断実施ではない。受信フィールド検証に限定し、8日間分析期限・同意・race-only条件を回避しない。

## 5. 実装順序と撤退条件
1. まず**純粋関数**の集計器と失敗注入のテストをDraftへ追加。既存receiverとの連結は行わない。
2. むせレビューでプローブの必要性自体を査定。API公式サンプルが取得可能なら、そちらを優先し本番プローブは省く。
3. リスクや費用をクリアした場合のみ受信経路組込みのPR差分を作成して再監査、Atsuo明示承認後に短期間だけ本番実施。
4. 実データで必須時刻/距離が確認できなければ自動受信案はNo-Go。端末内FIT解析等の代替へ切り替え。Heart Rateだけ欠ける場合は心拍を任意項目として扱うが、**ユーザーに黙って捏造・補間しない**。
