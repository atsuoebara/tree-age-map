## 何を証明しようとしているか
- 公開状態行の `SELECT ... FOR SHARE` 読み取りが、撤回トランザクションの `UPDATE` と競合すること。
- 撤回側が行ロックを先に保持したとき、読み取り側が待機し、コミット後には公開OFF/dirtyの状態を見てNULLを返すこと。
- 読み取り側が先にロックを保持したとき、撤回側が待機し、既存の読み取りトランザクションが終わるまで撤回コミットが完了しないこと。
- 古い世代の承認スナップショットは、再度enabledフラグだけをONにしても公開されないこと。
- 同じ撤回を再送しても世代が重複して増えない（試験上の冪等性）こと。

- `Synthetic JS gate checks` が成功し、12個のPASSが存在する。
- `Isolated PostgreSQL concurrent withdrawal and reads` が成功し、`B1_GATE_FIXTURE_READY`、二つの `EVIDENCE: ... PostgreSQL Lock`、三つの `PASS:`、`B1_GATE_POSTGRES_CONCURRENCY_COMPLETE` が記録される。
- GitHubのワークフロー完了がsuccessであることと、`tee` を含むシェルコマンドの `pipefail` により内部エラーを隠していないことを確認する。
- 失敗時はログ内の最初のSQLエラーまたはassertionを原因に分解し、修正後に**新しい実行**で確認する。

## 注意：DBのロック成功≠HTTPの撤回保証
- SELECTの結果を得た後、HTTPレスポンスを組み立てる前に撤回がコミットする場合、**DBロックだけでは撤回後の古い応答の到着を禁止できない**。共有ロックがトランザクション完了で解放されるため。
- CDN/ブラウザ/Service Worker・他端末で保存したスナップショットは、DBトランザクションの外にある。
- 実装段階では、公開APIの送信直前の停止・世代照合、応答キャッシュ禁止、並列撤回と要求、ネットワーク遅延、再送を含む別試験が必要。送信直前の世代再検証だけでも撤回と送信の間の競合窓を完全に消せないため、利用者向けの停止保証と反映タイミングを実測・設計する。
- 設計上の「撤回完了」表示は実際に保証できる停止範囲のみを約束する。第三者保存済みデータの完全削除は保証しない。
