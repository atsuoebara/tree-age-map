# A-4 年輪の節「保存済み1,817本 vs 対象1,434本」原因調査（2026-11-05）

**状態：調査記録のみ。コード、DB、データ、RLS、公開設定に変更なし。ユーザー本人の最終承認を受けたA-4第1～4弾は現行のまま。**

## DBを読み取り専用で実測した結果

- Supabase プロジェクト runners-rings（public.runs、deleted_at IS NULL）
- 保存済み1,817件に一致するユーザーが **1件のみ** であることを検証し、そのユーザーの集計のみを行った（個人識別子・各ラン名称・軌跡・生データは取得・掲載しない）。
- 1,817件の内訳：
  - source='strava': 1,435件。このうちstrava_id > 0は1,434件、IDなしが1件。
  - source='tcx': 328件。
  - source IS NULL: 46件。
  - source='garmin': 6件。
  - source='intervals': 2件。
- 合計 1434+1+328+46+6+2=1817、対象外 383件。
- 対象外のソース内訳：**328 TCX、46 NULL、6 Garmin、2 Intervals、1 Strava(IDなし)**。
- 各ソースの active 行は、今回集計範囲では started_at がすべて存在し、距離も正、route は全て2点以上のJSON配列を持つ（ただしGPS軌跡が有効/走種目と確証できる意味ではない）。
- TCXの activity_date は2013-06-06から2026-05-30まで、比較的古いランの記録が多数を占める。
- 詳細な個人別記録を公開ドキュメントへ転載しない。上記の件数は開発担当自身の対象として本人から明示されていた1,817本/1,434本と一致する集計のみ。

## 実装上の原因

- `a4-milestones-core.js` の `verifiedImportedRun()` は `source==='fit'`、または `source==='strava'` かつ有効な strava_id の行だけを種目確認済みとする。したがってTCX、source NULL、Garmin、Intervalsは現仕様で除外、Strava IDなし1件も除外する。
- `index.html` の `buildActivityFromTCXText()` は TCX Activity 要素の `Sport` 属性を読み、**属性が存在し値がrunning以外なら取り込みを拒否する**。しかし `Sport` 欄が空のTCXは拒否せず通る。`runs` テーブルに種目の確証・Sport属性を保存する列はなく、取り込み済み328件について「Runningが明記されていた」とはDBから証明できない。
- `started_at`、GPSポイント数、距離>0だけをもって「ランニング確定」と判定するのは不十分。
- 過去の取り込み（現在のパーサー導入以前）がどう処理されたかは、この調査だけでは確証しない。

## 結論と安全な次段階

1. **不具合ではなく、A-4の厳格な種目確認ルールに起因する母集団の差。** データは消えていない。A-4第4弾のカウントダウン「対象1434本、1500本目まで66本」は現仕様では正しい。
2. **本数対象を即座に1,817本へ拡大しない。** データの種目誤認と歴史的達成日の変動を避ける。ユーザーによる個別確認や当時のソースファイル/種目証拠の検討が必要。
3. 「TCXでSport=Runningが実際に明記されたケース」を将来の取り込みで保持する方法を設計できるが、昔の328件に一律適用してはいけない。
4. 他の46件のNULL source、6件Garmin、2件Intervals、Strava IDなし1件についても、出所・取り込み時の種目検証ができるか別途設計監査する。
5. ユーザーが望む場合、推定や一括更新ではなく、保存済みレコードを本人が一件ずつ確認・承認する段階的な方法を設計する（監査・ロールバック・プライバシー優先）。

## 監査で確認を求める事項
- 集計の母集団同一性（1,817件唯一のアカウントと対象1,434件）

- 書き込みなしでの証拠追加収集手順
- 既存A-4の節目を勝手に再計算対象拡大しないこと
