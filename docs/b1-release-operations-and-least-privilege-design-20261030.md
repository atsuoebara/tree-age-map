## 1. 職務分離と承認記録

1. 作成者（集計・匿名性評価担当）が対象 country_code / activity_year / generation / policy_version / rounded_distance_km / closed_after を確定し、T1〜T9証跡、最低人数・寄与支配・丸め・年締め結果を保護された審査記録に添付する。未確定なら保留。
2. 同意担当が実際の同意取得・撤回・失効処理と文面の対応を独立チェックする。合成未実装の現在は本番承認不可。
3. 独立審査者が匿名性と同意の根拠を照合。privacy_review_ref / consent_review_ref / reviewed_by / reviewed_at / accepted を承認し、原資料の保管場所と照合用ハッシュを内部記録する。本人による自己承認禁止。
4. 決定テーブル INSERT は専用の書込経路だけ。二人の異なるIDによるチェック・案件ID・時刻・対象世代を確認してから単一トランザクションで追記。既存行をUPDATE/DELETE/TRUNCATEしない。テーブルは追記専用で誤記修正不可のため、間違えた場合は公開停止→新世代の再審査。既存世代に同じ主キーで再INSERTできないことに注意。
5. 運用担当は決定を作成できず、承認済みの決定のみを使って b1_private_approve_year を実行。開始は別担当が全件整合を検証し、ユーザーの「本番適用」「同意受付」「一般公開」の各別途承認を確認してから b1_private_start を実行する。
6. 撤回・失効・異常時は公開停止を優先。b1_private_stop の実行権限は緊急停止専用担当にも付与。停止と旧世代からの再開拒否、台帳記録を検証する。
7. 台帳・審査証跡は内部保管のみ。未公開の距離値、同意情報、個人情報をGitHub、Actionログ、公開レスポンスに出さない。監査ではコード・匿名の判定結果のみ共有。

## 2. 権限設計（まだSQL GRANTを実行しない）

想定ロール: b1_review_writer（審査決定の専用追記経路のみ）、b1_approver（承認のみ）、b1_publisher（開始のみ）、b1_emergency_stopper（停止のみ）、b1_private_reader（内部読み取りのみ）。anon / authenticated に実行権・テーブル権を与えない。PUBLICを明示REVOKEする。いずれも原則 NOLOGIN ロールを使い、認証済み運用主体に必要な役割だけ割当てる。具体的な運用主体・接続経路・監査ログは別途確定。

### 重要な未解決設計差分

**現在の4関数はすべて SECURITY INVOKER**。そのため EXECUTE だけをGRANTしても関数内で参照・更新する rr_private テーブルの権限がなく、要求の「関数のみ・テーブル直接アクセスなし」は満たせない。単純なGRANTではなく、監査済みの SECURITY DEFINER 専用ラッパーを別途設計する必要がある。既存関数を無条件に SECURITY DEFINER へ変更してはならない。

ラッパー設計条件:
- 別個の NOLOGIN 所有者、最小限のテーブル権、限定した EXECUTE 権。所有者が不要に広い権限やBYPASSRLSを持たないこと。RLSと所有者のバイパス挙動を隔離環境で検証する。
- SECURITY DEFINER の固定 search_path、スキーマ修飾、呼出し元の識別・本人性確認、権限付与/剥奪、例外時のfail-closed、監査台帳の一貫性を試験する。
- 審査決定INSERTもテーブル直接INSERTを一般担当へ付与せず、二人承認済みの案件に限定する専用処理で行う。審査済みフラグの自己付与を禁止する。
- 読み取り経路は内部サーバーだけ。HTTP APIに公開する場合は認証・認可・キャッシュ禁止/失効・同時撤回を別途審査する。
- 停止のロック順序・トランザクションと事故時の復旧手順を文書化し、権限剥奪試験とマイグレーション・ロールバックを隔離DBで検証。

## 3. 監査受入条件

- 審査決定の実施者、独立審査者、必要証跡、案件番号、二重承認の技術的な担保が明確。
- 所有者権限、SECURITY DEFINER、RLSの関係が実DB相当の隔離環境で確認済み。
- 各ロールで許可された関数だけ成功し、すべてのテーブル直アクセス、横断実行、PUBLIC/anon/authenticated のアクセスが失敗。
- 不正決定の追記、二重承認、世代ずれ、公開開始の競合、撤回優先、台帳欠落が防止される。
- 正式同意・撤回合成、HTTP競合/キャッシュ試験、T1〜T9、数値と年締めの承認は別の残課題として維持。
- 上記をむせが独立監査。**本番適用・同意受付・一般公開はユーザーの個別承認があるまでOFF**。
