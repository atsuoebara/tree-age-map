# Rings Now：Safari通信とキャッシュ／旧タブ境界の検証（PR #124、2026-11-14）

## 対象と安全範囲
PR #123の合成FIT動的観測を引き継ぎ、**本PRは新規3ファイル（Node試験、文書、CI）のみ**を作る。既存の公開ページ、Service Worker、index、本番カレンダー、DB、FITパーサーには一切手を加えない。**実FITの使用・公開・本番ONは引き続き禁止。**

## 自動テストで確認すること
1. 現行sw.jsをNodeのvmにロードしてfetchイベントを模擬し、公開合成HTML、関連JS、FITパス、APIパス、その他の公開ページ、POST、外部ドメインにはrespondWithを設定せず、SWのCacheStorageにも触れないことを確認。
2. アイコンとトップページは例外。公開アイコンは既存rr-staticキャッシュ、トップのGETナビゲーションはnetwork-firstでno-storeを使用する。SWのキャッシュ対象がFIT、HTML解析ページ、JSへ広がらないことを確認。プリキャッシュのinstallイベントそのものはこのテストの対象外。
3. 古い独立タブの合成セッションを模擬して、pagehide→pageshow(persisted)、visibilitychange後は復活せず、他タブの有効性と混同しないことを確認。
4. 公開合成ページが依然としてSHA検証経由であり、手動失効を備え、CSPにconnect-src 'none'／form-action 'none'を持ち、本番フラグ2点はOFFのまま。

## 重要な未確認事項
本PRは**実機Safariのネットワークキャプチャではない**。Service Workerのソース上の分岐とNodeのイベント模擬を確認するだけで、SafariのHTTPキャッシュ、CDN/GitHub Pagesの配信残存、ブラウザ拡張、端末のプロキシ、ページ内JS全分岐、実際の古いタブの保有時間、実bfcacheでのイベント発火を保証しない。

現行SWが「対象外のリクエストを横取りしない」ことは、ブラウザ自体のHTTPキャッシュが残らないことや、閉じずにいる旧タブが保持する古いJSが安全に撤去できることとは**別問題**。本PR成功でも、方式Aの14証跡のうち「httpCacheAndServiceWorkerReviewed」「iosSafariLifecycleTested」「incidentRollbackAndOldTabPlan」を真とは扱わない。

## iPhone実機での次の検証（合成専用）
- Safariで公開合成ページを開き、合成FITを選択して5区間を確認。別タブ・別アプリへ移動し、戻ったら選択と結果が失効するか。必要ならページ再読み込み後にのみ再試行。
- Safariの「戻る→進む」と再読み込みで合成結果が復活しないか。既存のA〜E本人報告のEは模擬離脱であり、真のbfcache復帰とは区別。
- テストに実FITや個人スクリーンショットを使用しない。iPhone上で通信の実測をする方法、旧タブ強制撤去の非保証、配信停止時のキャッシュ残留のリスクは別の監査対象。
- 旧コードの配信停止とSafariタブの継続は別。公開済みページの取り下げだけで端末内の既存JavaScriptが消えると断言しない。

注意書き：信号待ちやトイレ休憩、自動ポーズなどの影響により、正しく分析できない場合があります。
